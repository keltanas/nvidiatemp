## Context

Greenfield: в репозитории нет кода. Целевая машина — Linux с драйвером NVIDIA 595.x, одна RTX 4080 (возможны несколько), X-сессия на `DISPLAY=:0`, passwordless sudo для обычного пользователя. Проверенные команды: чтение — `nvidia-smi --query-gpu=...` (без root), запись — `sudo DISPLAY=:0 nvidia-settings -a "[gpu:0]/GPUFanControlState=1" -a "[fan:0]/GPUTargetFanSpeed=N"`; чтение режима без root — `DISPLAY=:0 nvidia-settings -q GPUFanControlState`. Аппаратный минимум ручного режима карты — 30%. Требования см. в specs, мотивация — в proposal.md.

## Goals / Non-Goals

**Goals:**
- Надёжный демон: при любом выходе — карта возвращается драйверу (авто-режим).
- Чистое ядро: логика «измерения → решение» — чистые функции, тестируемые без GPU и subprocess.
- Один бинарник, кросс-компилируемый, минимум зависимостей.

**Non-Goals:**
- NVML-бэкенд (шов для него оставляем, реализацию — нет).
- Web UI, метрики Prometheus, история/графы.
- Поддержка Windows/macOS, GPU без вентилятора (laptop-складки без fan — не цель).

## Decisions

**D1. CLI-бэкенд за интерфейсом-швом.** Доступ к GPU абстрагирован в два интерфейса: `Reader` (температура, мощность, текущая скорость) и `FanSetter` (режим, скорость). Реализация v1 — subprocess: `nvidia-smi` для чтения, `nvidia-settings` для записи.
*Почему не NVML (`go-nvml`):* cgo + `libnvidia-ml`, а поведение `SetGpuFanSpeedV2` на GeForce с этим драйвером не верифицировано; CLI-цепочка пользователя проверена на целевой карте. Шов позволяет позже добавить NVML вторым бэкендом без переписывания контроллера.

> **Ревизия (NVML-бэкенд, `internal/gpu/nvml.go`).** Опасение про cgo оказалось несущественным (сборка без драйвера проходит — библиотека грузится `dlopen`'ом в рантайме), а зависимость от X — наоборот, фатальной: на headless-хосте `nvidia-settings` отвечает `ERROR: The control display is undefined`, и тогда не работает ни чтение режима, ни запись, а `restoreAll` при остановке молча проваливается. Поэтому бэкенд по умолчанию — NVML (`backend: auto` с пробой записи и откатом на `nvidia-settings`), а CLI-бэкенд остался запасным (`backend: nvidia-settings`). `nvmlDeviceSetFanSpeed_v2` / `nvmlDeviceSetFanControlPolicy` адресуют вентилятор явно, что снимает и риск из раздела Risks про маппинг `[fan:N]` ↔ `[gpu:N]` на многоGPU-машине.

**D2. Одно чтение за тик на все GPU.** За опрос — один `nvidia-smi --query-gpu=index,name,temperature.gpu,power.draw,fan.speed --format=csv,noheader,nounits` (все карты в одном процессе). Парсинг строгий: числа — float (`power.draw` дробный, `fan.speed` может быть >100 — принимаем как есть), ошибка парсинга = ошибка опроса.
*Альтернативы:* XML (`-x`) — тяжелее парсить, не даёт выигрыша; per-GPU запросы — N процессов на тик без пользы.

**D3. Реактивная логика тика, состояние режима — внутреннее.** Каждый тик для каждого GPU решение вычисляется функцией от (текущие измерения, текущий режим, время последней записи) → действие: `switch-manual+speed` / `update-speed` / `switch-auto` / `noop`. Явного FSM нет: все записи идемпотентны. Режим при старте читается один раз из железа (`nvidia-settings -q GPUFanControlState`) — это корректно подхватывает карту, оставленную в ручном режиме (как сейчас на целевой машине); дальше состояние ведётся внутри.
*Альтернатива:* чтение режима с железа каждый тик — лишний X-раунд каждые 2с без выигрыша; дрейф состояния (внешнее вмешательство) самоисцеляется следующей идемпотентной записью.

**D4. Одна команда на запись, sudo по euid.** Переключение режима и выставление скорости — одним вызовом `nvidia-settings -a "[gpu:N]/GPUFanControlState=1" -a "[fan:N]/GPUTargetFanSpeed=X"` (или только `GPUFanControlState=0` для возврата в авто). Если euid ≠ 0 — команда оборачивается в `sudo`. Везде `DISPLAY=:0`. Любая запись (режим или скорость) обновляет «время последней записи» GPU и подчиняется паузе между записями — это же гасит дребезг переключений режима.

**D5. Конфигурация: `gopkg.in/yaml.v3` + встроенные дефолты.** Структура конфига мапится YAML-тегами; при отсутствии файла/полей применяются дефолты (включая дефолтную кривую), затем валидация (точки строго по возрастанию температуры, скорости ∈ [30,100], порог мощности > 0). Ошибка валидации — stderr + exit(1) до старта цикла.
*Почему не JSON из stdlib:* человекоредактируемый конфиг с комментариями важнее нуля зависимостей; одна маленькая зависимость приемлема. Viper отклонён: избыточен для одного файла.

**D6. Логирование: `log/slog` → stderr.** Info — переключения режима и записи скоростей, Debug — тики. Под systemd stderr уходит в journald; интерактивно — в терминал.

**D7. Раскладка кода:**
```
main.go                 # dispatch подкоманд (stdlib flag)
internal/config/        # загрузка, дефолты, валидация YAML
internal/curve/         # чистая функция: температура → скорость (интерполяция + кламп)
internal/gpu/           # интерфейсы Reader/FanSetter + nvidia-бэкенд (subprocess)
internal/controller/    # чистая функция тика: (измерения, режим, последняя запись) → действие
```

**D8. Двухфазный возврат в авто (auto-cooldown).** После того как условия возврата (мощность < порога И температура < нижней границы кривой) впервые выполняются, GPU не переключается в авто сразу: скорость удерживается на минимуме (30%) в течение `auto_delay` (по умолчанию 5 минут), и переход в авто происходит только если за это время нагрузка не появилась — любой разрыв условий возврата отменяет ожидание, управление возвращается к кривой. Время начала ожидания хранится в состоянии демона на GPU (`IdleSince`) и выводится чистой функцией тика вместе с действием.
*Почему:* короткие всплески нагрузки (инференс-запросы) без ожидания вызывали бы дребезг manual↔auto — каждое переключение идёт через X-соединение, а авто-режим драйвера при возврате может кратковременно выкрутить вентилятор; ожидание на минимальных оборотах гасит такие циклы и одновременно не даёт карте перегреваться в паузах.

## Risks / Trade-offs

- [Хрупкий CSV-парсинг nvidia-smi] → жёсткие флаги формата (`csv,noheader,nounits`), unit-тесты на реальных снимках вывода с целевой машины; ошибка парсинга считается ошибкой опроса и попадает в политику 5 неудач.
- [Адресация `[fan:N]` при нескольких GPU не проверена] (совпадает ли индекс вентилятора с индексом GPU) → v1 работает на одной карте; перед активацией per-index записей на многоядерной машине перечислить вентиляторы через `nvidia-settings -q GPUTargetFanSpeed` и построить маппинг.
- [Доступ root к X-дисплею под systemd] (XAUTHORITY) → в юните задать `Environment=DISPLAY=:0` и, при необходимости, `XAUTHORITY=/home/<user>/.Xauthority`; запасной вариант — `xhost +local:`. Проверяется при деплое.
- [Задержка записи через X-соединение] → записи редкие (мёртвая зона + пауза 5с), приемлемо; чтение режимом не пользуется каждый тик.
- [Катастрофическая остановка (kill -9, сбой питания) оставляет ручной режим] → не устранимо программно; все штатные пути возвращают авто; в README — команда ручного восстановления.
- [`fan.speed` > 100% / дробные значения] → парсинг float, без «чисток»; целевая скорость всё равно клампится в [30,100].

## Migration Plan

Greenfield, миграции нет. Деплой: сборка бинарника → копирование на хост → установка `/etc/nvidiatemp.yaml` (пример из репо) → `systemctl enable --now nvidiatemp`. Откат: `systemctl disable --now nvidiatemp` (при остановке демон сам возвращает авто-режим), удаление юнита и бинарника.

## Open Questions

- Точная адресация вентиляторов `[fan:N]` при нескольких GPU — проверить на многоядерной машине до включения per-index записей (не блокирует v1).
- Нужен ли root под systemd `XAUTHORITY` или достаточно `DISPLAY=:0` — решается пробным запуском на целевой машине при деплое.
